# 即梦图片 → 本地 Wan2.2 视频生成加速方案（v1）

> 状态：设计方案，尚未执行代码改造与本机 GPU 基准。适用分支：`v1`，生产策略：`paragraph_jimeng_v1`。本文件只约定后续实施任务，不授权恢复已经暂停的生产任务，不触发付费 API。

## 1. 实际生产链路与优化目标

实际链路：文稿/配音和分镜规划 → **即梦云端图片候选** → 选图/人工确认 → **本地 ComfyUI + Wan2.2 I2V 14B 生成视频** → 技术检查、父片尾帧续接和人工连续性确认 → 原生帧超分 → 合成和交付。不要误把即梦视为视频生成云服务。

目标不是孤立的最快采样速度，而是提升 **质量验收通过的有效视频秒数 / 总生产墙钟时间**；同时保留支付幂等、来源验证、原始内容、两个图片候选、全部视频帧、场景连续性与人工审核机制。

仓库现有基础：`workflows/wan22_i2v_14b_api.json` 默认 40 步、CFG 3.5、high/low 双 UNET、Euler/simple、FP8 scaled；图中另有 4 步 / CFG 1 的开关，但没有证明正确加载对应蒸馏 LoRA，**不得直接打开 4 步开关进入生产**。`src/video_ai/planning/scene_clip_continuation.py` 固定 `steps=40`，并形成片段继承关系。

## 2. 避免重复实现的现状

2026-11-05 的 `docs/task-designs/video-generation-performance-results.md` 已记录以下优化：

- 普通/参考图：先持久化两个任务 accepted，再进行查询、下载、验证；未知提交不自动重发。
- 即梦下载的身份与完整性保护、TOS 有强版本时的复用、恢复路径、选图预览与邮件发送优化。
- Comfy 能力读取缓存与部分轮询优化、提帧/PNG 完整证明批处理、复制批次校验及合成解码合并。

上述历史测试为局部离线测试；没有证明真实即梦延迟或 Wan GPU 推理、整条成片流程提速。实施前先核对 v1 实际启用的配置和产物，不把旧工作结果误作新收益。

## 3. P0：完整性能基线和可观测性

为实验 run 增加不包含密钥、原文的结构化计时，至少记录：

| 阶段 | 指标 |
| --- | --- |
| 即梦提交 | 各候选请求预检、POST、accepted 持久化、受限排队 |
| 即梦等待 | task_id 对应的轮询次数、远端已完成时间、获取完成时间 |
| 即梦下载 | GET 下载、原图验证、候选通知与人工选图等待 |
| Comfy 服务 | 冷启动、热启动、模型装载/卸载、显存峰值 |
| Wan I2V | CLIP 编码、high-noise 采样、low-noise 采样、VAE、SaveVideo |
| 后处理 | 生成视频探测、trim、末帧提取、逐帧超分、最终合成与验证 |
| 全流程 | 单段时间 P50/P95、可用视频秒/墙钟秒、失败率、重做率 |

创建 `scripts/benchmark_jimeng_local_video.py`（或等价工具）与 JSON 报告，严格只读既有 run；真实推理样本必须使用新建的、明确授权的实验 run，绝不接触已暂停/正在处理的旧任务。推荐 3 种片段（低运动、高运动、场景续接），冷启动 1 次、热运行 ≥3 次，保持图、提示词、分辨率、种子、帧数一致。

验收：能够解释总时间中云端等待、GPU 采样、后处理和人为等待的比例；没有虚构加速倍数。

## 4. P1：无画质变化的代码路径优化

### 4.1 单事务内复用视频探测

检查 `src/video_ai/runtime/production_scene_clips.py::_technical`：新生成 `generated.mp4` 时，`generated_producer` 已执行 `inspect_video`；随后 `source_producer` 为 trim 再次 `inspect_video` 同一文件。可仅在同一次媒体事务的内存变量里传递已经验证的 `source_info`，避免重复完整探测。**恢复路径**中如果 `generated_producer` 因已有合法结果而未运行，仍必须执行原来的完整 `inspect_video`。保留 trim 产物完整核验和原媒体身份校验。

回归：新生成、从 generated 成功后恢复、篡改输入、错误 frame count、进程中断、未授权修改；检验产物 SHA/帧数/时间戳/证据与原路等价。

### 4.2 服务和数据准备重叠

实测拥有所有权的 Comfy 进程是否在同一个授权生成阶段重复装载模型；同一阶段下可复用模型驻留并重叠 CPU 图像准备与 GPU 采样。不能让 worker 并行持久化不可变任务证据；所有写入仍在持锁的协调线程完成。不得跨人工审核无限期保留 GPU 服务。

### 4.3 依赖感知调度

`production_scene_clips` 中父子片段有尾帧和人工观察依赖；必须保持**同一连续链串行**。不同场景的 CPU 工作允许有限预准备，独立场景的云请求并发必须基于明确资源/成本约束，且绝不跳过前置选图与审核。

## 5. P1 实验：独立高速 Wan 推理配置

新增与原图隔离的 `wan22_i2v_14b_fast_api.json` 和 mapping/provenance，保持原 `wan22_i2v_14b_api.json` 字节不变。

按顺序、每次只引入一项变化：
1. 使用明确匹配 **Wan2.2 I2V 14B high/low 双专家** 的蒸馏/LightX2V LoRA，验证模型路径、强度、步骤数、CFG 与输出。
2. 在 Windows RTX 5090D V2 的具体 CUDA/PyTorch/Comfy 组合上验证 SageAttention，不因社区经验默认开启。
3. 再评估兼容的 TeaCache/MagCache 或其他缓存方案；必须分别核验双专家与跨帧一致性。
4. 最后评估 `torch.compile`、显存驻留和组合收益；冷启动编译成本单独记录。

配置档位：`quality` = 原 40 步基线；`fast_experimental` = 独立加速图。模型/LoRA SHA、workflow hash、节点版本、attention backend、cache、采样步数/CFG、Comfy 版本全部纳入**新任务**的冻结身份、request/graph/恢复证据。旧 pending/accepted/unknown 的生成身份绝不变更或重新 POST。

必须检测：黑帧/NaN、闪烁、角色与纹理一致性、颜色漂移、运动稳定、尾帧接缝、完整帧数/PTS、GPU 峰值显存和失败重试。质量显著下降时不得自动推广为默认。

## 6. P2：即梦图片链路的进一步优化

双候选“先提交、再收集”已实现，不应重复改造。先测真实云端每阶段耗时；只有在 API 配额、费率和幂等机制明确后，才考虑**不同独立场景间有界窗口**（初始并发 1 或 2，依据限流实测调整）。每个付费请求必须在网络 POST 前有 durable intent，完成后有原 task ID；提交未知不自动重试/换新任务；远端下载失败只能恢复既有 task，不能重复计费。遵循批次依赖，不突破人工选图门槛。

## 8. 明确非目标

不改变原始文稿/TTS、不删减内容、不降低候选数/视频帧数、不跳过人工选择或连续性验收、不偷偷降低最终输出画质、不把离线局部基准外推成整片耗时、不把即梦图片生成误写成云视频生成。
