# 旅行者 2 号重复读取修复（2026-11-12）

## 结果

在现有 08 版素材上，完整只读审核准备和退出检查成功完成。最终应用层统计：

- 内容读取 12,525 次，涉及 12,525 个不同文件，重复路径为 0。
- 单独流式哈希读取 3,784 次，涉及 3,784 个不同文件，重复路径为 0。
- 原先在准备阶段被读取 478 次的 `04/production/scene-revision/request.json`，现在整次准备只读取一次。
- 总耗时从本轮修改前的 384.438 秒降至 370.023 秒。重复读取已消除，但整体仅减少约 3.7%；不能宣称冷启动已变快到秒级，剩余主要成本仍是对象构建、规范化和结构检查。

这些是 Python 应用层读取计数，不等于物理磁盘 I/O。内容读取同时计算该份原始字节的 SHA256；“单独流式哈希”不包含这部分。不得把哈希回调数量减少单独当成所有读取数量的减少。外部编解码工具为技术检查读取媒体的工作不由这两个计数器计量。

最终原始数据：`.tools/clip-review/repeated-reads-verified-20261112.json`。同目录机器可读汇总：`2026-11-12-repeated-reads-results.json`。

## 根因与修改

1. JSON 解析、修订原始字节读取、哈希检查原来各自打开同一文件。新增受保护字节读取入口，一次读取同时保留原始字节与完整 SHA256；配置、修订、审核原始提交、脚本及提示词合同复用它。返回的 JSON 对象仍重新解析，避免调用者修改共享对象。
2. 保护窗口中的原生只读句柄在短验证会话结束后仍有效，但旧代码没有继续复用，导致退出检查重新哈希。现在窗口仍有效且身份检查通过时继续复用；已关闭窗口、可写文件、可变 manifest 保持重新读取。
3. 实测 JSON 集合超过 64 MB，旧缓存被占满。调整为按需分配、最多 1 GiB 的批次缓存，单个文本文件最多 64 MiB。最终实际缓存 684,353,723 字节，批次结束释放；这是增加内存以减少重复文件读取的代价。超过资源上限或平台无法提供强制只读保护时，仍保留完整读取回退。
4. 6 个约 8.6–11.5 MB 的 `invalidation.json` 超出旧单文件 8 MB 门槛，导致各读取两次。提高门槛后，已先用这 6 个真实文件验证 6 次读取，再在完整测量中验证无重复。
5. 审核入口共用一次场景上下文。旧任务脚本改用批量 API；准备和批量提交之间保持保护窗口。仅审核模式还会保护已完成默认 Wan 片段的固定媒体和记录，避免它们被当成可写输出反复哈希。观察和回执按既有协议只能新增或核对，不能覆盖；因此新文件仍可原子创建，创建后可复用读取。目录清单检查保留，进度输出保持原逻辑。生成入口不启用此模式，其他渲染协议维持原策略。

## 正确性边界

- 缓存命中依然检查原生句柄、文件身份、元数据和规范路径；文件变化被拒绝，不仅凭 mtime 复用。
- 进入写入范围会释放相应可写文件的句柄并清除字节缓存。关闭窗口不会把旧缓存带到下一次运行。
- 缓存命中仍向每个依赖捕获器传递文件身份，目录和缺失路径检查保留。不会因为缓存而产生审核通过记录。
- 只提交审核的安全入口为 `scripts/submit_scene_clip_reviews.py`。旧 `.tools/accept_voyager_frame_review_and_continue.py` 仍保留原有后续生成行为，本次未执行它。

## 验证与现场

221 项相关测试通过，包括跨短会话复用、源文件变化、写入晋升清缓存、关闭/复制上下文、依赖捕获、大 JSON、固定片段媒体、仅新增的回执/观察、上游参考输入以及独立输入加载的临时保护窗口。额外执行过的生产输入测试有 3 项字体/TTS 预检失败；在进程内恢复原 JSON 读取和原输入加载实现后，同样的 3 项仍失败，未修改这些无关行为。

最终现存 `clip.json` 数量仍为 137；正式 `observation-accepted.json` 数量为 0。没有启动 Wan、ComfyUI、放大或全片合成，没有伪造或提交生产审核记录。没有删除已有素材或回退无关工作区修改。

完整实测是只读提交准备，不是一次真实审核落盘耗时。提交中的固定媒体复用与仅新增回执边界由针对性回归测试验证，未以生产审核写入充当性能测试。

独立调用 load_frozen_inputs 时也建立临时受保护读取窗口，消除首次加载内部的重复读取；若调用者已有窗口，则复用已有窗口。窗口关闭后的再次调用重新验证新内容，不跨无保护间隙使用旧缓存。
